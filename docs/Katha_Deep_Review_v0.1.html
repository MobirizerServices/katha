Fix first

The eight items that make the current build unsafe to put money behind, in the order I would take them. Each is a real, reachable defect, not a hardening wish.

  1. Close the free-coins endpoint (C1)
    POST /v1/web/orders credits any authenticated caller with no payment proof and no production guard. One line makes it fail closed like IAP already does.
  2. Make debits atomic in the database (B1, B2)
    Balance checks run against a per-worker snapshot; two concurrent unlocks both succeed and the wallet goes negative. A failed flush then wedges that worker's ledger for every user.
  3. Namespace idempotency keys by user and reject mismatched replays (B4)
    A client-chosen unlock key can pre-empt another user's check-in or web purchase key, silently zeroing their credit.
  4. Require a real OTP provider and real Apple verification in managed envs (B3)
    A deployment that passes the production guard still logs anyone into any phone number with any four digits.
  5. Validate drafts and refuse non-positive prices at the ledger (A1, A4)
    A content-role draft with coin_price −100 pays users to unlock; a draft with the wrong shape 500s the public catalog with no way to delete it.
  6. Make the admin guard require OIDC config and put the admin vhost behind an allowlist (D1, A2, A6)
    With the shipped QA compose and a blank issuer, the one-click dev identity provider is live on public 443.
  7. Move the web site's access and price decisions to the server (S1, S2, S4)
    The site decides "free" and "unlocked" from a constant and localStorage, contradicting the repo's core convention.
  8. Ship StoreKit 2 and Keychain storage in the iOS app (I1, I2)
    The app sends a fabricated receipt, so purchases cannot work against a real backend, and the 30-day bearer sits in plaintext UserDefaults.

Filter by severity

B · Ledger, persistence and shared infra

CriticalReproducedB1
Concurrent unlocks double-spend; wallets go negative
backend/packages/infra/katha_infra/persistent_ledger.py:131-141 · db.py · Dockerfile KATHA_WORKERS=4

Every mutation is refresh → in-memory rule → flush with no transaction or lock across the three steps, and each gunicorn worker and each service holds its own PersistentLedger. Scenario: a 60-coin wallet receives two 60-coin unlocks on two workers; both refresh, both pass the balance check, both persist. Reproduced with two threads on one SQLite file: 20 of 20 rounds succeeded twice and the wallet row ended at −60. The same window exists between admin adjustments and core-api unlocks.

Fix: make the debit one database transaction with a row lock on the wallet (or a conditional UPDATE … WHERE balance ≥ cost), and treat the in-memory ledger as a cache rather than the arbiter.

CriticalReproducedB2
A failed flush wedges the worker's ledger for every user
backend/packages/infra/katha_infra/persistent_ledger.py:43-57

On IntegrityError the retry re-mints transaction ids but reuses the same entitlement list, so a (user, episode) collision from two workers fails again and raises. The pending tail is never dropped, so every later flush on that worker hits the same error while the in-memory ledger keeps applying credits it cannot persist. Scenario: double-tap unlock across two workers → one worker's flush raises; a later 10-coin purchase for an unrelated user on that worker raises too, memory says 20, database says 0, and those rows vanish at restart. Reachable from free-episode playback as well as paid unlocks.

Fix: recompute the entitlement set after refresh and drop rows already on disk; on a second failure roll the in-memory state back or crash rather than serve unpersisted money.

CriticalReproducedB3
Production guard does not require an OTP provider or Apple verification
backend/packages/infra/katha_infra/prodguard.py:50-56 · core-api/app/routers/auth.py:142,154-166

OTP verify only checks the code when KATHA_OTP_PROVIDER is set, and Apple sign-in hashes whatever string the client sends with no verification in any mode. Scenario: KATHA_ENV=prod with all required secrets and Postgres passes the guard; any four digits log into any phone number, and user ids are sha256(phone)[:16] so the victim account is derivable. The Apple path also mints a different user per login in production because Apple's identity token changes each time.

Fix: require KATHA_OTP_PROVIDER (not console) and Redis when workers > 1 in managed envs; verify the Apple identity token against Apple's JWKS and derive the id from its sub claim; fail closed like iap_verify.

HighReproducedB4
Idempotency keys share one global namespace and unlock accepts the client's key verbatim
backend/packages/ledger/katha_ledger/ledger.py:59-67,137-143 · core-api/app/routers/wallet.py:162,185

Keys are not scoped by user or checked against the replayed payload, and the unlock endpoints pass the client key straight through into the same namespace as server-minted keys. Scenario: an attacker unlocks an episode with key checkin:usr_victim:2026-09-03 and web:usr_victim:coins_web_popular_in → the victim's check-in returns already_claimed and their ₹199 web order credits 0 bought coins. Any user replaying another user's key gets a 200 carrying the other user's spent amounts and no entitlement.

Fix: prefix client keys server-side (unlock:{user}:{key}); in the ledger raise a conflict when the existing transaction's user, type or reference differ from the request.

HighTracedB5
Alembic baseline is create_all from live models, so the first real revision cannot apply
backend/migrations/versions/0001_baseline.py:19-29 · .github/workflows/ci.yml:34-37

The baseline imports Base and runs create_all, so CI's upgrade head plus alembic check on a fresh database can never detect a model change, and once 0002 exists a fresh environment gets its column from the baseline and 0002 fails with "column already exists". Downgrade drops every table. Scenario: add a column, CI green, QA (stamped at 0001, autocreate off) throws UndefinedColumn at runtime.

Fix: freeze the baseline as explicit op.create_table DDL (autogenerate once and commit it) and never import the models from a migration.

HighTracedB6
Twilio provider can never verify a code
backend/packages/infra/katha_infra/otp.py:70-75,80-104

Twilio Verify generates and sends its own code; the send call posts only To and Channel, but verify compares against the locally generated code. No user can log in with the Twilio provider selected.

Fix: call VerificationCheck in verify for Twilio, or send CustomCode (needs account enablement).

HighReproducedB7
Audit chain breaks under concurrent appends and cannot be repaired
backend/packages/infra/katha_infra/shared_store.py:346-358 · admin_app/main.py:130-140

Append reads the last row then inserts with no serialization; two threadpool handlers take the same prev_hash. Reproduced with 20 concurrent appends and no tampering: chain_ok is False permanently, indistinguishable from an attack. The audit row is also committed in a separate transaction from the money move it records, so a crash in between leaves an unaudited adjustment.

Fix: lock a single chain-head row inside the same transaction as the mutation (or enforce a unique prev_hash and retry).

MediumReproducedB8
Audit hash omits actor role, IP and user agent, and deleting the newest rows is undetected
backend/packages/infra/katha_infra/shared_store.py:350-352,377-384

The hash covers prev|ts|actor|action|target|detail only, joined with a pipe. Rewriting a row's role, IP or user agent and deleting the tail both leave chain_ok True; with no secret an attacker with database write can rewrite any row and recompute the rest.

Fix: hash all columns with unambiguous encoding (JSON), HMAC with a server secret, and anchor the head hash out of band.

MediumReproducedB9
Ledger accepts a zero or negative unlock cost
backend/packages/ledger/katha_ledger/ledger.py:149-172

Cost 0 with un-owned episodes raises KeyError (500); a negative cost passes the balance check and min(bonus, cost) turns the debit into a credit. Reproduced: balance 100 → 600 with the episode entitled. This is what A1 exploits from the admin side.

Fix: raise LedgerError when cost ≤ 0 and episodes remain to unlock; validate price_per_episode > 0.

MediumTracedB10
Every wallet read, playback and mutation loads the whole transaction and entitlement tables
backend/packages/infra/katha_infra/persistent_ledger.py:89-92 · shared_store.py:104,274

refresh issues unfiltered SELECTs on both money tables per request per worker, and admin adjust/refund build a fresh PersistentLedger per call, reloading the entire ledger. Cost grows linearly with platform history on the hottest paths.

Fix: fold in rows above a high-water mark id, or drop the process cache in favour of per-request reads once B1 is fixed.

MediumTracedB11
OTP is four digits, resends reset the attempt counter, and limits are per-process
backend/packages/infra/katha_infra/otp.py:43-49,54,93-104 · core-api/app/routers/auth.py:32-77

Defaults allow roughly 150 guesses per phone per 10 minutes. Without Redis the code store and counters are per worker, so with four workers caps multiply by four and verify on a worker that did not mint the code fails about three times in four.

Fix: six digits, attempts carried across resends, resends capped, and Redis required in managed envs.

MediumTracedB12
Invoice numbers use the calendar year, not the Indian financial year
backend/packages/infra/katha_infra/shared_store.py:770 · comms.py:159

A purchase on 10 Feb 2027 is numbered KATHA-INV-2728 although it belongs to FY 2026-27, and the statutory sequence resets on 1 January. The stamp is UTC, so late 31 March UTC is already 1 April IST.

Fix: compute the FY from the IST date with an April boundary.

LowReproducedB13
KV value column is String(1024) but stores whole draft series and experiments
backend/packages/infra/katha_infra/models.py:79-80 · admin_app/main.py:1220

SQLite ignores the length (a 2205-char draft stored fine in dev); Postgres raises on the first long synopsis in QA. Fix: use Text, and cap input lengths in the handler.

LowTracedB14
Unicode digits pass isdigit and crash compare_digest
backend/packages/infra/katha_infra/otp.py:100 · core-api/app/routers/auth.py:135

Arabic-Indic digits satisfy the format check and then raise TypeError inside the timing-safe compare, a 500 in real-OTP mode. Fix: require isascii() as well.

LowTracedB15
Retry path re-mints a transaction id the client already received
backend/packages/infra/katha_infra/persistent_ledger.py:52-54

The router has already returned the original object, so the client holds an id that never exists in the database and refunds by that id 404. Fix: mint ids from the database or return the re-minted transaction.

CriticalTracedD1
Following the QA runbook as written exposes one-click admin sign-in on public 443

What is solid

The review is fair only if it says where the design holds. These are the parts I would keep exactly as they are.

  • The pure ledger. Side-effect free, append-only log as the source of truth, bonus-first spend, negative-balance block, reconcile-from-log, and tests that assert real invariants. The defects are in the persistence adapter and callers, not the rules.
  • Stream token signing. HMAC over prefix, user and expiry with a normalised path scope check that closes traversal and prefix-walk; the public media route refuses video outright.
  • OIDC core. PKCE S256, state and nonce in a signed short-lived cookie, RS256 via JWKS, issuer/audience/expiry required, email_verified and hosted-domain checks, role always from the server directory, fixed callback redirect, CSRF header on mutations.
  • Money-desk guardrails. Approvals are idempotent by id, self-approval is blocked server-side, refunds are IDOR-safe and bounded, typed confirms guard pricing and flags, last-admin and tombstone guards prevent lockout and resurrection.
  • Client discipline in the admin panel and iOS app. Both render server state for balances and lock state, carry idempotency keys on unlocks, and never optimistically debit; the admin contract drift test genuinely parses the client against the generated inventory.
  • Containers and repo hygiene. Non-root users in every image, TLS 1.2/1.3 only, HSTS and frame denial on both vhosts, no secrets, databases or media tracked in git.
